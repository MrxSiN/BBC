# Brainfry analysis and optimization priorities

The competitive objective remains **NOT YET ACHIEVED**. The measurements in
[the benchmark report](08_BENCHMARKS.md) identify different problems in build
latency, generated execution, memory and file size. Improvements in one do
not establish improvements in the others.

## Why Brainfry is faster and smaller

| Dimension | Brainfry implementation | Current BBC + XAX implication |
|---|---|---|
| Complete build | One native process parses, optimizes, emits bytes and writes a container; no external assembler/linker | BBC invokes its frontend and canonical importer, verifies a much larger graph, binds the process host and uses legacy bootstrap lowering. The matched v3 sixteen-case geometric means are about 1.14–1.17 seconds versus about 27 ms for Brainfry. Frontend-only tuning cannot close that gap. |
| Arithmetic | Consecutive same-direction arithmetic becomes an immediate-count operation | Transparent v1 retains individual commands. Optional v3 now packs power-of-two adds/subtracts; direct arbitrary deltas and generic generated-code overhead remain. |
| Common loops | `Zero`, offset `MulAdd` and stride `Scan` remove common loop work | BBC now folds exact unit-step clear loops in Brainfuck. Affine transfer and scan recognition still need proofs and implementation before XAX lowers their declared semantics. |
| Backend | Dedicated x86-64/AArch64 emitters hold the tape cursor in a register and patch branches directly | XAX is a general verified backend; measure graph/operation and spill costs before targeted graph or backend changes. A second BBC machine-code writer would violate the repository architecture. |
| Startup and tape | Fresh native processes reserve address space and commit initially zero OS pages; a small freestanding runtime provides I/O | BBC's reusable decision contract resets all 65,536 cells for every invocation. Fresh-process and repeated-call costs need distinct measurements; removing reset would be incorrect. |
| Build memory | Compact Rust operations and byte buffers | The current BBC caller uses a lazy zero-initialized 64 MiB importer view and releases it before verification/lowering. The matched v3 compiler resident peaks remain about 51 MiB versus 5.3 MiB for Brainfry. Extent is not resident RAM. |
| Native file size | Direct minimal PE/ELF writers and compact optimized instruction stream | The matched v3 file-size geometric means remain about 14,183 versus 2,890 bytes on Windows and 2,743 versus 1,140 on Android. Further folding and generic backend/package costs need separate accounting. |

These explanations follow the pinned
[optimizer](https://github.com/DirazCoder/brainfry/blob/e55d45735a6feb450a7e47852f4340f5b532fef8/bfc/src/optimize.rs),
[native compiler](https://github.com/DirazCoder/brainfry/blob/e55d45735a6feb450a7e47852f4340f5b532fef8/bfnative/src/main.rs),
[x86-64 emitter](https://github.com/DirazCoder/brainfry/blob/e55d45735a6feb450a7e47852f4340f5b532fef8/bfnative/src/codegen/x86_64.rs)
and [project documentation](https://github.com/DirazCoder/brainfry/blob/e55d45735a6feb450a7e47852f4340f5b532fef8/README.md).
The causal attribution is implementation analysis, not an isolated per-pass
timing experiment. Numeric comparisons retain their existing report's
workload, process and target boundaries.

## Correctness limits found during analysis

The release Windows native compiler reproduces these defects:

| Source | Required behavior | Observed optimized native behavior |
|---|---|---|
| `+[++].` | Never terminates: adding two preserves an odd controlling cell | Exits successfully and emits `00` |
| `+[--].` | Never terminates: subtracting two preserves an odd controlling cell | Exits successfully and emits `00` |
| `+[<>-].` | Fails on the first left move from cell zero | Exits successfully and emits `00` |
| `+[+++].` | Terminates and emits `00` | Correct control case |

The clear-loop recognizer accepts any folded add/subtract count without an
odd-step termination proof. The offset-loop recognizer records net offsets
and cell effects but can lose an intermediate movement with no target-cell
effect. Its generated `MulAdd` correctly guards a zero source and checks the
declared target; that does not recover movement discarded by recognition.

Nontermination above follows the modulo-256 parity invariant; reference
budget exhaustion is only a diagnostic, not the proof. The failing left
movement is common to both projects' profiles. These cases are correctness
checks, not runtime races. They do not invalidate already verified common
workloads or exclude the entire competitor. Preserve exact output/status
validation and disclose any ineligible workloads individually.

Brainfry's growable tape and EOF-leaves-cell behavior also differ from BBC.
Brainfly uses unchecked span accesses and stops its instruction chain on EOF.
The twelve smoke cases stay within safe low tape indices and supply every
consumed input byte. Full-profile error behavior is not comparable.

## Implemented first optimization

BBC's count-high capacity comparison formerly ran after every decoded raw
byte. The frontend now computes a Boolean full flag only when the instruction
count carries to a new 256-command group. Each byte tests that flag instead.
Command acceptance, diagnostics, source consumption and BFX output are
unchanged. This is an actual Brainfuck source
change, with a [proof and measurements](07_OPTIMIZATION_PROOFS.md#p0-carry-triggered-capacity-flag).
It adds 82 executable instructions and no tape cells. It does not fold
application instructions or remove the larger XAX build-stage bottleneck.

An earlier command-gated candidate was rejected after its paired measurements
showed instruction-heavy and own-source regressions. Its complete samples
are retained separately in the evidence; they are not final-candidate samples.

Across ten fixed native frontend inputs, the retained change's geometric mean
of per-case median ratios is 1.169x on Android and 1.086x on Windows. The
Windows nested-input median is about 4% slower, with an exploratory interval
including parity. Its compiler DLL grows 20,992 bytes; the Android compiler
library remains 50,120 bytes. Application BFX stays identical. These gains
and costs are scoped to BBC frontend calls, not a new competitor score.

Windows and Android execution are verified: each passes three identical native
frontend generations and 393 importer cases. The initially disconnected Pixel
became available during the follow-up. Earlier Android evidence remains
attached to the previous frontend hash; the new run has its own report.

## Implemented semantic optimization

The optional [v2 pass](10_BFX_V2_CLEAR.md) now recognizes exact `[-]` and `[+]`
and removes groups of 256 identical arithmetic commands. This is actual
Brainfuck implementation with canonical XAX importer changes. It preserves
transparent v1, the complete tape reset and intermediate movement checks.
Neither even-step negative case becomes CLEAR. Full-wrap empty loop bodies
retain their nonterminating nonzero-entry behavior.

The [proof and correctness record](07_OPTIMIZATION_PROOFS.md#p1-clear-loops-and-full-arithmetic-wraps)
covers independent interpretation, all-byte input, boundaries and native
rebuilds on both targets. The new complete build/process/resource comparisons
retain all twelve original sources and add four preregistered clear-loop
workloads. They use equal OS-backed zero-initialized importer buffer setup in
both BBC arms and release that workspace before verification/lowering. This
external caller configuration must not be attributed to the semantic pass or
compared directly with the older buffer-retention report as a measured win.

## Next measured steps toward the competitive objective

The [v3 arithmetic pass](12_BFX_V3_ARITHMETIC.md) is now EXECUTED: fourteen
powers, 432 native properties, 72 independent cases, 908 cross-target records,
22,120 full-buffer calls and three generations of all three components on
both targets. It uses actual BF recognition and canonical XAX lowering;
complete-build/process/resource timing remains a separate report. The first
byte-width rotate declined on Windows and was repaired canonically with a
supported 32-bit rotate/truncate sequence.

1. Complete and measure the canonical XAX native build path, including its
   outstanding diagnostic, self-store, large-edit and DLL gates. Reuse proofs
   only through the existing verified cache contract. This addresses the
   largest recorded build-latency gap; do not bypass verification.
2. Extend compact arithmetic beyond powers where useful, with proved actual XAX
   lowering support. The v4 monotone movement pass now preserves
   first-crossing failures; prioritize general odd-step clears next. Retain v1 as the
   transparent differential path and a capacity-safe fallback.
3. Keep recognition in Brainfuck and lower declared operations in canonical
   XAX through expected-root transactions. Extend to guarded affine
   transfers and scans only after bounds, wraparound, entry and termination
   equivalence pass. Include the defects above as negative cases.
4. Measure and reduce importer workspace retention and generic graph/package
   overhead, keeping safety checks and full logical reset. Report actual
   whole-build tree memory and full executable size.
5. Add Brainfly's now-runnable JIT and NativeAOT modes to counterbalanced
   trials; resolve the remaining LLVM/MLIR comparators, translated references,
   broader corpus and real-app gates. Keep Android and Windows results separate.

Each step needs its own correctness, full-pipeline time, RAM, file-size and
execution measurements. None of the competitors is marked SURPASSED by this
follow-up.

The [v3 measured follow-up](13_V3_BENCHMARKS.md) reduces this corpus's build
time and native-call cost against v2 in aggregate. Brainfry still retains
much faster complete builds and smaller files. Its valid scored workloads
remain included; the reproduced defects do not remove them.

The [v4 movement contract](14_BFX_V4_MOVEMENT.md) and [matched report](15_V4_BENCHMARKS.md)
add guarded identical-direction groups. Both-target full-buffer checks and
four-component native fixed points pass. Affine transfers, stride scans and
complete native compiler-host integration remain open. The v3 figures in
the implementation table are a separate pinned measurement snapshot.
