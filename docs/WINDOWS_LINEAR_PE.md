# Windows x64 — bounded Brainfuck linear compiler

**Iteration 39, experimental.** A Linux-executed, self-hosted-BF-built *standard Brainfuck program* now emits a complete, source-dependent PE32+ executable. This goes beyond the fixed exit-image seed from Iteration 38, but **is not yet a complete Windows Brainfuck compiler**. The new `.exe` files have not been executed by a Windows loader.

## Actual scope

| Contract | Current behavior |
|---|---|
| Compiler logic | `experiments/windows_linear_pe_64.bf`, 10,831 standard BF commands |
| Source filtering | Existing `experiments/android_source_scan.bf` (BF-owned, ordinary noninstructions ignored) |
| Accepted executable commands | `+`, `-`, `>`, `<` only |
| Source size | 0–64 executable instructions; 1 MiB adapter raw-input ceiling |
| Data tape | 65,536 zero-initialized bytes; initial pointer at cell zero |
| Cell arithmetic | Unsigned 8-bit modulo 256 |
| Bounds checks | Every pointer movement checked; out-of-bounds executes x86 `UD2` |
| PE image | Fixed 2,048-byte PE32+ console image with `.text`, `.idata`, `.tape` sections |
| I/O | `.` and `,` rejected; no byte I/O yet |
| Loops | `[` and `]` rejected; no jump relocation yet |
| Windows execution | **NOT RUN**; no Windows loader or Wine here |
| Windows self-hosting | **UNIMPLEMENTED** |

The BF writer emits its own PE headers, imported `KERNEL32.dll!ExitProcess` metadata, machine-code prologue, command-specific x64 slots and exit sequence. The transport adapter does not generate machine instructions or rewrite PE fields. The script `tools/author_windows_linear.py` helps author the saved BF source and is development-only. That script is **not** part of normal compilation.

`UD2` is a deterministic instruction trap in the generated machine code, but its target Windows exception mapping/exit behavior is **not verified**. The absence of a `.reloc` table means loader behavior outside the preferred-image mapping has not been verified. Section permissions are structural assertions until tested on Windows.

## Compile a supported program

```sh
printf '>+<' > /tmp/windows-test.bf
python3 bootstrap/run_windows_linear.py /tmp/windows-test.bf /tmp/windows-test.exe
objdump -p /tmp/windows-test.exe
objdump -d -j .text -Mintel /tmp/windows-test.exe
```

The source scanner accepts standard Brainfuck input (ignored characters included), produces the filtered command stream and a count/status trailer, and the adapter forwards only its filtered output to the BF compiler. The BF compiler emits a 2,048-byte PE image followed by its own status byte. The adapter checks framing and writes the result atomically only for success. No Python lexical scanner, assembler, Windows linker, or native code generator participates in this production path.

## Tests and acceptance evidence

```sh
python3 tests/verify_windows_linear_pe.py
python3 tests/verify_windows_pe_exit_seed.py
python3 tests/verify_source_comments.py
python3 tools/check_docs.py
```

The focused suite generated and examined **87** programs, checked five independently interpreted BF writer executions, accounted for **60** reference pointer traps, rejected seven invalid/over-limit writer inputs and confirmed three atomic CLI output-preservation cases. PE structures, relocatable RIP-relative startup addressing, fixed 12-byte command slots and the imported exit path were checked; `objdump` recognizes the native instructions/import table. These tests verify emitted code bytes and semantics for the supported subset, not actual Windows loader behavior. See [`../evidence/iteration39_windows_linear_pe.json`](../evidence/iteration39_windows_linear_pe.json).

## Prepared Windows loader smoke suite (not executed here)

Four images generated by the BF stage are bundled in `build/windows39_acceptance/`, with a SHA-256 manifest and target-side PowerShell runner `verify_windows39.ps1`. On an actual Windows x64 machine, run from that directory:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\verify_windows39.ps1
```

The runner validates hashes, launches only these four deterministic programs, records OS version and exact exit/output results, and writes a JSON result. All four should exit zero with no output **if the Windows loader accepts these prototypes**. That is a prediction, not recorded execution. Avoid counting this smoke suite as a compiler S2 or full semantics test: the supported instructions do not expose tape values through output yet.

## Next gates

1. Run the existing exit image and at least the empty, arithmetic and pointer-trap generated PE programs on an actual Windows x64 system/VM. Capture OS build, loader results, stdout, stderr, exact exit/exception code and image hashes.
2. Implement Win32 `GetStdHandle`, `ReadFile`, `WriteFile` and EOF-to-zero with correct 16-byte stack alignment, shadow space and redirected-stream behavior—all machine bytes emitted by Brainfuck.
3. Add BF-owned bracket matching and x64 branch displacement patching; expand source capacity with checked size/layout calculations.
4. Execute the Brainfuck compiler on Windows and demonstrate repeated native self-compilation, without foreign production codegen. Then expand semantics, safety and performance evidence.

The Android native S2 result is separately recorded from supplied device evidence. Its **300,000-command universal target** is still open.
