# Iteration 35 — Android tape rebase and larger linear source images

## Implemented

Added [`../experiments/android_tape_rebase.bf`](../experiments/android_tape_rebase.bf), a standard Brainfuck ELF post-layout stage compiled by the existing Brainfuck-only Linux native compiler. The stage moves the writable tape segment to a page-aligned virtual address beyond the RX code, updates the AArch64 `ADRP` startup, and repairs executable segment size bytes crossing the 64 KiB boundary. It consumes only validated transport copies of ELF fields and the complete ELF previously generated by Brainfuck stages. Python does not calculate or insert the new addresses or machine instructions.

The opt-in CLI adds `--multiclass --tape-relocated`. It handles **2,000 linear commands** in six aligned ELF file-size classes. Loop-containing programs remain limited to **1,024 commands** due to the existing bounded BF relocation table. The previous writers remain available and their generated artifacts are not silently changed. See the detailed [source notes](../experiments/android_tape_rebase.bf.notes.md).

## Verification

The new stage is **3,061 standard BF instructions** and its Linux-native executable is **98,167 bytes**. The stage itself does not need a foreign assembler. The [machine-readable evidence](../evidence/iteration35_tape_rebase.json) records source/native hashes and focused test counts. The test covers segment layout, instruction encoding, the 1,354→1,355 RX/tape collision boundary, the 1,695→1,696 file-class transition, 8-bit arithmetic, raw I/O, nested loops within the old 1,024 limit, pointer traps, invalid source rejection, and atomic CLI file preservation. Simulated programs are compared against the reference BF interpreter at two load biases. `readelf` accepts the new 2,000-command image.

- New BF source compiles to a byte-identical Linux-native executable from both commented and filtered variants.
- Previous 512-slot BF bracket-relocation suite passed separately.
- Fresh Linux native self-compilation Stages 1 and 2 each produced the installed **475,703-byte compiler byte-for-byte**. The independent cold Stage 0 was not rerun. See the [native replay evidence](../evidence/iteration35_linux_native_replay.json).
- The full older Iteration 34 randomized-suite replay exceeded the execution limit and is **incomplete**, not passed or failed on demonstrated semantics.
- No new Android device or Android loader execution was performed. Android-native compiler execution and target-side S2 remain **unimplemented**. Windows x86-64 PE32+ remains **unimplemented**.

## Source and external dependency roles

`compiler/core.bf` remains the authoritative Linux compiler and is unchanged. The new backend stage's authoritative code is `.bf`. The Linux native compiler is used to compile that stage; Python is a validated byte transport and test harness, not a source parser/optimizer or ELF patcher. The AArch64 instruction simulator and `readelf` independently inspect the output but are not production dependencies.

## Known limitations and next priority

The tape segment placement is now BF-owned for the six documented file-size classes, but this is not general-purpose relocation. The loop patcher still has a 1,024-command ceiling; the 2,000-command path is **linear-only**. Next expand bracket patching beyond 1,024, verify additional page classes and run generated code under the actual Android loader, then port and self-host the compiler natively on Android. The ultimate 300,000-command target remains far from proven. The original 22-iteration baseline remains an estimate, not a guarantee of remaining work.
